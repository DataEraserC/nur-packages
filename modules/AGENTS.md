# NixOS 模块规范（DataEraserC fork 自有模块）

本文件只覆盖 `modules/` 下 fork 自有模块的约定；包定义、包元数据与工作流规则见[仓库根 AGENTS.md](../AGENTS.md)。

- **自有模块放在 `modules/` 并在 `flake.nix` 的 `nixosModules` 注册**（`# My additions` 段）：模块会被 `flake-modules/_internal/modules-test-nixos-config.nix` 自动编入测试用的 `nixosConfigurations`，因此 `enable` 默认 false 时也必须能正常求值（默认值用 `pkgs.<pkg> or null` 之类，避免未应用 overlay 时求值失败）。
- **自有模块选项统一加 `dataEraserc` 前缀**：`services.dataEraserc.<name>`（如 `services.dataEraserc.cliproxyapi`）或 `hardware.dataEraserc.<name>`，避免与将来 nixpkgs 官方同名选项冲突；`flake.nix` 的 `nixosModules` 注册名不加前缀，因为 `builtins.attrValues self.nixosModules` 要求平铺结构。
- **与 nixpkgs 同名模块共存时用 `dataEraserc` 命名空间，不要用 `disabledModules` 接管**：自有模块选项已在 `services.dataEraserc.<name>` 下声明（如 `services.dataEraserc.cliproxyapi` 与 nixpkgs 的 `services.cliproxyapi`），命名空间互不冲突，直接共存即可（两个 `enable` 默认都为 false）。误用 `disabledModules = [ "services/misc/cliproxyapi.nix" ]` 会把 nixpkgs 模块连同其 `meta.doc = ./cliproxyapi.md` 手册锚点一起从求值中剔除，而 `nixos/doc/manual/redirects.json` 是静态文件、仍引用 `module-services-cliproxyapi` 等锚点，`nixos-manual-html` 会报 `RedirectsError: Keys of the redirects mapping must correspond to some identifier in the source` 导致 `system.build.toplevel` 构建失败（`documentation.nixos.checkRedirects = false` 只是掩盖症状，禁止提交）。确需整体替换 nixpkgs 模块时才用 `disabledModules`（路径相对 `modulesPath`），且必须同步处理被删模块的文档锚点。
- **服务内置从 GitHub 下载的静态面板时，用 store 路径 + 关闭自动更新实现离线**：CLIProxyAPI 的 `/management.html` 由 `managementasset.FilePath` 解析，优先读 `MANAGEMENT_STATIC_PATH`（目录则取 `<dir>/management.html`），文件不存在才联网；模块传 `MANAGEMENT_STATIC_PATH = <runCommand 面板目录>` 并在默认设置里加 `remote-management.disable-auto-update-panel = true` 即可离线且不写只读 store，`runCommand` 里用构建期 `[ -e <pkg>/management.html ]` 判断，兼容只提供 `index.html` 的面板包。
- **运行期密钥优先用 `._secret`，不要用会改变行为的 `MANAGEMENT_PASSWORD`**：后者会强制 `allow-remote=true`（绕过 `remote-management.allow-remote`）；用 `utils.genJqSecretsReplacement { loadCredential = true; }` 把 `managementKeyFile`（默认自动生成到 `${stateDir}/management.key`）通过 `remote-management.secret-key._secret` 注入，`allow-remote` 才会生效且密钥不进 store。
- **可写配置文件用「首启 seed 一次」开关**：GUI/管理 API 会写回配置文件，每次 activation/启动都用 Nix 值覆盖会丢失运行期改动；把 nixpkgs 风格的 secret 替换脚本（`utils.genJqSecretsReplacement ... .script`）包在 `preStart = if mutableConfig then ''if [ ! -e ${configPath} ]; then ${script}; fi'' else script;` 里，默认 seed-once，设 `mutableConfig = false` 则每次声明式重写。
- **seed-once 的配置文件必须让 secret 轮换显式失效**：`config.yaml` 里存的是已解析的密钥值，轮换后 seed-once 会让**旧密钥永远留在盘上**（服务继续接受旧密钥）。做法：把 credential 内容摘要（`sha256sum $CREDENTIALS_DIRECTORY/<tag> | sha256sum`，tag 取 `secretsReplacement.credentials` 里 `"<tag>:<path>"` 冒号前的部分，注意**不能**用 `lib.escapeShellArg` 包 `$CREDENTIALS_DIRECTORY`，单引号会阻止运行时展开）与求值期的 settings 指纹（`builtins.hashString "sha256" (builtins.toJSON settings)`）一起写进 `${stateDir}/.config-fingerprint`：credential 变 → 先 `rm -f config.yaml` 让 seed 重新生效；settings 变 → 只 `echo ... >&2` 警告（直接重写会丢面板改动）。写 marker 前先 `rm -f` 再 `printf >`，避免旧所有者让 `chmod 0600` 在 `set -e` 下失败。
- **seed-once 的配置里"网络地址"类键要改用 CLI flag 强制，不要只靠警告**：settings 指纹只能告警的规则对监听地址不成立——端口改动是主机间移植的常态（旧 `config.json` 会永远绑住旧端口，防火墙却按新 `settings` 开洞，服务实际没监听），而 `-listen`/`-web-listen` 这类 flag 会**覆盖文件并被上游写回**（opencode2api 1.3.7 实测），不丢 WebUI 的密钥/代理等状态。做法：`startCommand` 在 `-config` 后拼 `listenArgs`，`extraArgs` 放最后（Go flag 后者覆盖前者，保留逃生口）；同步改掉"keeps winning"警告措辞与 `mutableConfig` 选项说明，避免文档说谎。验收用 `nix eval` 看 `serviceConfig.ExecStart` 里 flag 真的出现（WebUI 关闭时不能带 `-web-listen`）。
- **seed-once 首启检查用 `! -s`（size>0）而非 `! -e`（exists）**：`jq > file` 重定向在 exec 前就会 truncate 目标文件，jq 失败后留下 0 字节残桩；`! -e` 判定文件已存在不再 seed，app 永久解析空文件崩溃。用 `[ ! -s config.json ]` 可在 jq 崩溃后自动重试 seed。同时**把 marker 写入放在 seed 之后**：seed 失败则 marker 不更新，下次启动重新检测到 credential 变化并重试，实现自愈。
- **应用启动时 `os.Chdir` 到可执行文件目录会让 `WorkingDirectory=` 彻底失效**：Go 程序常用 `os.Executable()` + `os.Chdir(filepath.Dir(exe))` 定位自身资源（如 m365-copilot2api），工作目录永远是只读的 store 子目录。凡是“优先读 `*_DATA_DIR`、否则退回相对路径/tmpdir”的变量只设 `*_DATA_DIR` 覆盖不全，写入会以 `open ./xxx.tmp: read-only file system` **静默失败**（接口照常 200，只丢数据）：模块必须把每个持久化路径都用绝对路径环境变量显式指向 `stateDir`（对照上游 Dockerfile 的 env 清单，**再加上 Dockerfile 也漏掉的相对路径项**，可在源码里 grep 默认值）。验证：`journalctl -u <unit> | grep "read-only file system"` + 检查 `stateDir` 里是否真的出现了这些文件。**复查日志必须按新实例的启动时间过滤**（先 `systemctl show -u <unit> -p ExecMainStartTimestamp` 再 `journalctl --since`），否则旧实例的报错会被算进来，把“已修好”误判成“仍有问题”。
- **secret 轮换要感知“落盘优先”的上游逻辑，优先用 `*_BOOTSTRAP_FILE` 而不是复制明文**：这类网关常在首次读到明文密码后哈希写入 `admin-password.json`，之后启动只认该文件（`*_DATA_DIR` 的优先级还高于 `*_ADMIN_PASSWORD_FILE`），于是模块 `ExecStartPre` 每次覆盖的明文再也不会被读取——轮换 secret 后控制台密码静默保持旧值。正确做法：用上游的一次性 bootstrap 变量（`*_ADMIN_PASSWORD_BOOTSTRAP_FILE`，只在持久化文件不存在时生效）+ systemd credential（credential 已 chown 给服务用户、模式 0400，**服务进程自己就能读**，不需要 `+` 的 ExecStartPre 把明文 `install` 进 `stateDir`），再用 sha256 标记文件（`${stateDir}/.<name>.sha256`）比对 credential 内容：变了就 `rm -f` 持久化文件让 bootstrap 重新生效，没变则保留（管理员在控制台改的密码不会被每次启动冲掉）。标记方案要先用假 credential 在临时目录跑完整状态机（首次/未变/轮换/空文件/文件缺失）；升级时要顺带删除遗留的明文副本。
- **`Environment=` 不做 specifier / 变量展开**：`%d`、`$CREDENTIALS_DIRECTORY` 都会原样保留，所以不能靠它把 credential 的真实路径喂给应用。可行做法：(1) `ExecStart` 指向 `pkgs.writeShellScript` 包装脚本，在脚本里读 `$CREDENTIALS_DIRECTORY/<name>` 后 `export` 应用需要的变量（也能 `export FOO="$(cat ...)"` 传 secret，避开 `EnvironmentFile` 的转义坑）；(2) 直接用固定路径 `/run/credentials/<unit-name>/<name>`。注意 `Environment=` 里写的 secret 会出现在 `systemctl show` 输出里，wrapper 里 export 的不会。
- **模块的路径与断言必须真的可写、也必须能被求值**：
  - 不要声明应用根本不读的选项：加预留参数（如 `extraArgs`）前先确认上游有命令行解析（`grep -rn 'flag\.\|os.Args' cmd/ api/`）；`stateDir` 不是 `/var/lib/<name>` 时不能靠 `StateDirectory=` 创建，此时 `ReadWritePaths=` 引用不存在的路径会让 `ProtectSystem=strict` 的 unit 启动失败
  - `stateDir`、`authDir` 等可写目录按 `builtins.dirOf dir == "/var/lib"` 分成两组：在 `/var/lib` 下的进 `StateDirectory`（直接传列表，systemd 会逐个创建并 chown 给 `User`），其余进 `ReadWritePaths`，activation 里再 `install -d -m 0700` + `chown` 兜底——只覆盖 `stateDir` 是不够的（旧版 `cliproxyapi` 模块设 `authDir = /var/lib/cpa-auth` 时该路径完全没被覆盖）
  - 断言 message 必须写实际命名空间（`services.dataEraserc.<name>.*`），自定义 `user`/`group` 用 `builtins.hasAttr cfg.user config.users.users` 校存在性；`package = null` 时不能直接写 `lib.getExe cfg.package`（断言生效前就抛类型错误），要写成 `if cfg.package != null then lib.getExe cfg.package else "${pkgs.coreutils}/bin/false"`，让断言给出可读报错
- **activation script 中的 `umask` 必须用子 shell 隔离**：所有 activation snippets 在同一个 bash 进程里顺序执行，一个 snippet 的 `umask 077` 会泄漏到后续 snippet；`etc` snippet 的 `setup-etc.pl` 若在 077 下 `make_path`，`/etc` 目录会变成 0700，非 root 用户读不到 `/etc/systemd/user.conf` 等文件，所有 systemd user manager（包括 GDM greeter）都会报 `Permission denied` 而无法启动桌面。修复：`(umask 077; openssl rand -base64 32 > keyfile)`；注意 `if` 块不会创建子 shell，`umask` 在 `if` 内外都有效。
- **`runCommand` 等自建派生必须自己创建 `$out`，模块改动必须用 `nix build` 实证**：`pkgs.runCommand` 只运行脚本、不做安装动作，`ln -s`／`cp ... $out/x` 会报 `No such file or directory`（`install -D`、`cp -r` 才自带建目录语义），脚本开头统一 `mkdir -p $out`；这类错误只在模块被真正构建时暴露（`nix eval` 只证明路径求得出来），所以模块改动的验收标准是 `nix build .#nixosConfigurations.<host>.config.system.build.toplevel` 真的构建成功。
- **Node/V8 服务的 unit 严禁 `MemoryDenyWriteExecute=`**：V8 在 `v8::Isolate::Initialize` 阶段就要把 JIT 代码页从 r-x 改为 rw，MDWX 下 node 起来即 fatal（`# Check failed: 12 == (*__errno_location ())`，栈顶 `v8::base::OS::SetPermissions`），直接 core dump（node 24 实测必现，包内 node 24 与宿主 node 同样如此）。凡是跑 node/deno 等带 JIT 运行时的 unit 一律省略这一行，其余加固照常；复现验证：`systemd-run --user --wait --pipe -p Type=oneshot -p MemoryDenyWriteExecute=true node -e "console.log(1)"`。
- **上游自带 sd_notify 集成的服务用 `Type=notify` + `NotifyAccess=all`，并 e2e 实测 READY**：READY/WATCHDOG 常由主进程派生出的子进程发出（如 OmniRoute 在 `server.once("listening")` 里由 server-ws 发 READY），`NotifyAccess=main` 会丢消息导致 start 超时；`systemd-notify` 不带 `--pid` 时不发 MAINPID，主 PID 仍是启动脚本，而它不带 `--no-block` 时会等 manager 处理完消息才退出，所以 unprivileged 发送者也能正确归属。NixOS 生成的 unit 默认 PATH 已含 systemd（未设 `path` 的 caddy.service 也带 `systemd-261.1/bin`），无需为 `systemd-notify` 单独加 `path`；`WatchdogSec` 要留出上游 ping 周期的两倍余量（OmniRoute 每 60s 一次则 ≥120s）。验收必须真起 unit 看 `ActiveState=active`，只求值证明不了 READY 能到。e2e 还要测停机：OmniRoute 收 SIGTERM 后正常 drain 完以 exit code 143 退出（journal 记 `code=exited, status=143`），不配 `SuccessExitStatus = [ "143" ]` 时每次干净的 `systemctl stop` 都会被记成 `Failed with result 'exit-code'`，停机检查以 `systemctl show -p Result` 为 success 为准。
- **不要用 CLI 启动器的 bin，直接 exec 上游的 standalone server 入口**：Node 应用常把 `bin/<name>` 做成交互式启动器（9router 的 `bin/9router` 在 stdin 非 TTY 时**无条件**进 tray 模式：把 server 作为 `detached: true` 子进程 spawn、`unref()`，还去 `npm install` systray2 并启动托盘），这类 launcher 在 unit 里会留下孤儿进程、让 SIGTERM 只打中 launcher（server 靠 `process.kill(-pid)` 才被杀），并且**每次启动前主动清理**：`ps aux` 里凡是命令含 `next-server` 的进程全部 `kill -9`、外加 `lsof -ti:<port>` 杀掉占用端口者——在共享主机上会误杀别的服务。模块应当直接 `exec node <pkg>/lib/node_modules/<npm 名>/app/{custom-server,server}.js`（`custom-server.js` 存在时优先，它注入真实 socket IP），并自己用 systemd 的环境变量喂 `DATA_DIR`/`HOME`/`HOSTNAME`/`PORT`；`npm` 的安装目录用 package.json 的 registry 名（`lib/node_modules/9router`），不随 `pname` 变。验收：`ps -ef` 里该 unit 只有 1 个 node 进程、`systemctl stop` 后端口立刻释放、无遗留进程。
- **Next.js standalone 的 `start-server` 把 SIGTERM 变成 `process.exit(143)`，unit 必须配 `SuccessExitStatus = [ "143" ]`**：`next/dist/server/lib/start-server.js` 的 signal handler 是 `case 'SIGTERM': process.exit(143)`（SIGINT 是 130），所以干净停机在 systemd 里记成 `code=exited, status=143` 而非 `code=killed`，不配该行时每次 `systemctl stop` 都被判为 `Failed with result 'exit-code'`。**用 bash 的 `$?` 无法区分这两种情况**（信号退出在 bash 里同样得 143，容易误判成"已经正常了"），要用 `os.waitpid` 读 `WIFSIGNALED`/`WEXITSTATUS` 才能确认，或用 `systemctl show -p Result` 验收（应为 `success`）。
- **模块的 e2e 加固验收：`ProtectHome=true` 会让放在 `$HOME` 下的 `stateDir` 直接 `EACCES`**：在 `/home/<user>/...` 里跑临时单元会报 `mkdir: permission denied`／`EACCES: permission denied, mkdir '<stateDir>/.9router'`，这不是模块缺陷而是测试位置选错——验收时把 `stateDir` 放在 `/var/lib`（配 `StateDirectory=`）或 `/tmp`（配 `ReadWritePaths=`），别放 `$HOME`。另外 `PrivateUsers=true` 下 `RuntimeDirectory`/`StateDirectory` 会被重映射、`ReadWritePaths` 指向宿主路径会报 `226/NAMESPACE`，故临时单元验收 hardening 时用 `ProtectHome=false` + 工作区内的 `stateDir`，或干脆只验 `ProtectHome` 之外的项；`CapabilityBoundingSet=`（空值）在 `--user` 会话里会因拿不到 capability 报 `218/CAPABILITIES`，临时单元里要省略。
- **沙箱里跑临时 systemd 单元的两个坑**：`systemd-run --user --unit=<名字>` 在部分环境（本仓验证沙箱）对**命名**单元恒报 `Failed to connect to user scope bus via local transport: No data available`，而不带 `--unit` 的自动命名可用；同时 `--property=Type=simple` 后立刻退出也会命中同一报错，`-p Type=oneshot --wait --pipe` 则稳定。可靠做法是让 systemd 自己命名并**从 `Running as unit: <name>` 输出里抓单元名**，再 `systemctl --user show -p ...` 查询；要跑长驻服务就写一个 oneshot 包装脚本（脚本内部自己 `&` 起服务、探测、`kill` 收尾）。临时单元只能执行 store 里的可执行文件（脚本要 `writeShellScript` 进 store 或用绝对路径的已存在脚本，工作区里相对路径会 `203/EXEC`）。
