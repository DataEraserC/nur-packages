# lobsterai-unwrapped 打包经验

LobsterAI（网易有道，MIT）是 Electron 43 桌面应用，Linux 侧**上游完全不发布产物**：更新接口 `api-overmind.youdao.com/openapi/get/luna/hardware/lobsterai/prod/update` 只有 `windowsX64`/`macIntel`/`macArm` 三个 key，GitHub releases 也没有资产（issue #273 正是在要 Linux 版），CI 虽然 `electron-builder --linux` 但产物不发布。因此只能源码构建，且必须自己补齐上游 `dist:linux` 里被省略的部分。

## 派生结构

- `default.nix`（`lobsterai-unwrapped`，unwrapped——目录名与 `pname` 都带 `-unwrapped` 后缀，包名上写明它是未包装的裸构建产物）：`build` → `tsc` + 双 vite + `compile:electron`，然后手工拼装目录而不是跑 electron-builder（避免 AppImage/deb 工具链与 electron 下载），用 nixpkgs `electron_43.dist`。只产出 `$out/opt/lobsterai` 原始应用树，**没有 `bin/`、没有 desktop 条目、没有图标安装**（`meta.mainProgram` 也随之移除——元数据检查只在产物存在 `bin/` 时校验它），它不是给人直接启动的。
- `../lobsterai-wrapper/default.nix`（`lobsterai-wrapper`）：轻量启动包装包，`inherit (lobsterai-unwrapped) version`、`passthru.unwrapped = lobsterai-unwrapped`。`makeWrapper` 指向 `${lobsterai-unwrapped}/opt/lobsterai/LobsterAI`，承载全部启动逻辑：`--no-sandbox`、`LD_LIBRARY_PATH`（stdenv.cc.cc.lib，见关键坑）、desktop 条目、hicolor 图标、ozone 平台自适应 flag（见下条）。调启动逻辑只重建这个秒级包，不再触发重型 lobsterai-unwrapped 重编。
- **ozone 平台自适应 flag 照抄 nixpkgs qq**：`--add-flags "\''${NIXOS_OZONE_WL:+\''${WAYLAND_DISPLAY:+--ozone-platform-hint=auto --enable-features=WaylandWindowDecorations --enable-wayland-ime=true --wayland-text-input-version=3}}"`。转义链：Nix 把 `\''${` 输出成字面 `\${` → installPhase 的 bash 在**构建期**不展开它 → makeWrapper 收到纯文本 `${NIXOS_OZONE_WL:+...}` 并转义写进 wrapper 脚本 → **运行期**展开。若误写成 `''${...}`，构建期就展开成空串（沙箱里两个变量都没有），flag 静默消失、构建照样成功。双闸门语义：会话同时有 `NIXOS_OZONE_WL`（本机 GNOME Wayland 会话全局设了 =1）和 `WAYLAND_DISPLAY` 才追加 wayland flags；ssh/waypipe 远程会话没有 `NIXOS_OZONE_WL`（sshd 不透传环境），继续用显式 `--ozone-platform=wayland` 启动即可，两者叠加无冲突。
- `openclaw-runtime.nix`（`lobsterai-openclaw-runtime`）：从 openclaw 源码打 64 个补丁构建 cfmind 运行时。
- `mkSkill`（文件内 let 绑定）：`web-search` / `pptx` / `imap-smtp-email` 三个技能各自一个 FOD + 小派生。

## 关键坑

- **`npmConfigHook` 不是 pkgs 顶层属性**，`callPackage` 直接声明会报 `Function called without required argument "npmConfigHook"`（提示里会误导向 `pnpmConfigHook`）。正确写法是声明 `npmHooks` 并用 `npmHooks.npmConfigHook`。
- **structuredAttrs 下顶层属性和 `env.*` 都会被导出**（实测 `runCommand { __structuredAttrs = true; env.BAR=...; TOPLEVEL=...; }` 两者都能读到）。所以 `npmDeps` 再写一份 `env.npmDeps` 会直接报 `The env attribute set cannot contain any attributes passed to derivation`；两者二选一即可，取顶层写法（同时是构建输入、nix-update 也读得到）。
- **上游不提交任何 lockfile**（LobsterAI 根目录、`SKILLs/*` 都没有），全部自行用 `npm install --package-lock-only` 生成后入库；`fetchNpmDeps` 用 `postPatch` 把 vendored lockfile 拷进源码树（官方 hint 就是这么写的），并且主派生的 `postPatch` 也要拷同一份，`npmConfigHook` 会 diff 两边是否一致。
- **技能依赖不是由 `build:skills` 装的**：那个脚本只管 web-search/tech-news/email。真正装全的是 `scripts/electron-builder-hooks.cjs` 的 `beforePack`，它遍历 `SKILLs/*/package.json` 逐个 `npm install`（实测产物里有 node_modules 的是 `web-search` 34M、`pptx` 37M、`imap-smtp-email` 7.3M）。`pptx` 依赖 `playwright`，其 postinstall 会拉浏览器，Nix 里走 `npm ci --ignore-scripts`（与实测产物一致：里面也没有浏览器）。
- **`build-openclaw-runtime.sh` 第 5 步会 `rm -rf node_modules package-lock.json` 再跑无 lockfile 的网络 `npm install --omit=dev`**，沙箱里必挂。用 `openclaw-runtime-offline.patch` 改成保留 lockfile，并在 `pack-openclaw-workspace-deps.cjs` 之后 `cp` 进打包态的 `cfmind-package.json` / `cfmind-package-lock.json` 再 `npm ci`。这两个文件是从一次成功构建的 `resources/cfmind/` 里取出来的**最终状态**（已含 workspace 依赖被改写成 `file:workspace-packages/*.tgz`、已删 devDependencies、已加 `@opentelemetry/api`），`pack-openclaw-workspace-deps.cjs` 必须先跑，否则那个 `file:` tarball 不存在。
- **openclaw 源码树必须 `git init` + commit**：`apply-openclaw-patches.cjs` 末尾会对 openclaw 源码跑 `git reset HEAD .`，fetchFromGitHub 的产物没有 `.git` 会失败。
- **openclaw 的 control-ui 构建不可字节复现**：连续两次构建有 1130 处差异，全部是 `assets/*-<hash>.js` 的 chunk 名不同，把 8 位 hash 归一化后内容完全一致。因此**不能**把整个 cfmind 构建包成固定输出派生（输出永远对不上声明哈希），只能是普通输入寻址派生。
- **`npmRoot` 不能写 `$NIX_BUILD_TOP/...` 这种要展开的变量**：钩子里是 `pushd "$npmRoot"`，bash 不会二次展开，必须写成相对源码根的路径（`../lobsterai`）。
- **dsh 运行时在 Linux 上根本没有**：`package.json` 的 `dsh.runtimes` 只有 mac-arm64/mac-x64/win-x64 三个 URL，实测产物 `resources/` 里也没有 dsh 目录；`dshEngineManager` 找不到运行时只 `console.warn` 后降级，不影响启动。所以不打包 dsh（早期的 `dsh-runtime.nix` 只解压 16KB 的 npm tarball、不装 72 个依赖，是坏的，已删除）。
- **Electron 侧不用 asar**：手工拼装用 `resources/app/` 目录，`electron-builder.json` 里那几个 `asarUnpack`（`better-sqlite3`/`@img`/`npm`）自然就不需要了。`better-sqlite3` v13 自带全平台 `prebuilds/linux-x64.node`，`hasInstallScript` 为假，不编译。
- **`process.resourcesPath` 取决于可执行文件位置**：`electron_43.dist`（即 `$electron/libexec/electron`，已 patchelf）整个拷到 `$out/opt/lobsterai/` 后必须把里面的 `electron` 改名成 `LobsterAI`，否则它会指向 nixpkgs electron 自己的 resources 目录，`cfmind`/`SKILLs` 全找不到。
- **修 `dontStrip = true` 和 `dontPatchELF = true`**：fixup 的 `patchelf --shrink-rpath` 会删掉 `$ORIGIN` 相对 rpath，把 electron 与 native `.node` 模块打坏。
- **native `.node` 模块缺 `libstdc++.so.6`，要在 wrapper 里补 `LD_LIBRARY_PATH`（现属 lobsterai-wrapper）**：手工拼装的 electron 不走 `autoPatchelfHook`，cfmind 运行时里的 linux glibc `.node`（better-sqlite3、tree-sitter 系等 7 个）直接 `ldd` 报 `libstdc++.so.6 => not found`，有模块还要求 `GLIBCXX_3.4.32`（实测 gcc-13 libstdc++ 最高 3.4.32 恰好够、gcc-15 到 3.4.34 更稳，主包自己的 12 个 `.node` 只要 3.4.29）。修法：`makeWrapper … --prefix LD_LIBRARY_PATH : "${lib.makeLibraryPath [ stdenv.cc.cc.lib ]}"`——wrapper 环境变量会被 Electron spawn 出的 cfmind gateway 子进程继承，一处覆盖主进程与运行时。注意拆分后这行在 `lobsterai-wrapper` 里，**unwrapped 的二进制直接裸跑会缺 libstdc++**，排查底层问题时要从 wrapper 脚本里抄上 env。排查手法：`find <out> -name '*.node' | grep -Ev 'musl|darwin|win32|arm'` 逐个 `ldd | grep 'not found'`、`readelf --version-info` 取所需 `GLIBCXX_*` 最高版再对 gcc-lib 各版本的 `strings` 产出。
- **`npmConfigHook` 装完依赖后无条件跑 `npm rebuild`，会把任何带 `binding.gyp` 的依赖就地编译**：2026.10.16 新增的 `selection-hook`（LobsterAI 桌面取词依赖，`install: node-gyp-build`）因此在 `lobsterai-unwrapped` 与 `lobsterai-openclaw-runtime` 两个派生里都炸——先报 `gyp ERR! find Python`，补 python3 后报 `X11/XKBlib.h: No such file or directory`。两处都设 `npmRebuildFlags = [ "--ignore-scripts" ]`，因为重编译产物根本进不了包：最终树来自 `installPhase` 的 `npm ci --omit=dev --ignore-scripts`，且上游 tarball 自带 `prebuilds/linux-x64/selection-hook.node`。跳过编译不代表运行时没事，这个 prebuild 的 `DT_NEEDED` 是 `libevdev`/`libX11`/`libXtst`/`libXfixes`/`libwayland-client`，所以 `lobsterai-wrapper` 的 `LD_LIBRARY_PATH` 要一并带上（外加原本的 `libstdc++`）：实测裸 env `require` 该 prebuild 报 `libevdev.so.2: cannot open shared object file`，带 wrapper env 后返回 `TextSelectionHook`。
- **`registry.npmjs.org` 的 `@img/*` 系列 tarball 走 HTTP/2 偶发 `Stream error in the HTTP/2 framing layer`**，构建会报 `builder failed`，重试即可，不是哈希问题。
- **`build-openclaw-runtime.sh` 里的第二次 `pnpm install` 是否重建整棵 `node_modules` 取决于 pnpm 版本**：`pnpmConfigHook` 已装好依赖并 `patchShebangs`，脚本再跑一次 `pnpm install --frozen-lockfile --ignore-scripts` 时，pnpm 12.9.0 只补 4 个链接（保留已 patch 的 shebang），而 pnpm 12.3.4（例如 nix-config 在 2026-10-01 的 nixpkgs）会重装 1338 个包，把 `tsdown` 等 `.bin` 的 shebang 还原成 `#!/usr/bin/env node`；沙箱没有 `/usr/bin/env`，随后 `pnpm exec tsdown` 报 `ERR_PNPM_CLI_EXEC_SPAWN: Failed to spawn command "tsdown": No such file or directory`。修法：设 `env.OPENCLAW_BUILD_ALL_NO_PNPM = "1"`，让 build-all 用 `node node_modules/tsdown/dist/run.mjs` 直接跑而不是经 `pnpm exec`（上游为无 pnpm 环境提供的开关；`plugins:assets:*`/`ui:build` 也有等价的 node 回退）。已实测：同一 nixpkgs rev（`c59305b`）下加该 env 后完整构建通过。

## store 里的插件清单会被 openclaw 判为 `unsafe plugin manifest path`

网关启动时报 `plugins.entries.<id>: plugin <id>: unsafe plugin manifest path: /nix/store/…/third-party-extensions/<id>/openclaw.plugin.json`，弹窗「openclaw.json is invalid」。根因链：

- `loadPluginManifest(rootDir, rejectHardlinks = true)` 默认**拒绝硬链接**；fs-safe 的 `openRootFileSync({rejectHardlinks:true})` 见 `nlink>1` 就报 `hardlink`。
- Nix store 靠 `.links` 做内容去重，**store 里的普通文件 nlink 恒 ≥2**（实测插件 manifest nlink=6~8），必被拒。已实证：同一个 manifest 用 `@openclaw/fs-safe` 直调，`rejectHardlinks=true → ok=false`、`rejectHardlinks=false → ok=true`。
- 唯一放行点是 `src/plugins/hardlink-policy.ts` 的 `shouldRejectHardlinkedPluginFiles`：`origin==="bundled"` 放行，否则要求 **`OPENCLAW_NIX_MODE==="1"` 且插件根在 `/nix/store`** 才放行。而 LobsterAI 把这些插件写进 `plugins.load.paths`（见其 `main.js` 的 `{load:{paths}}`），origin 是 `"config"`，不走 bundled 分支。
- **不能开 `OPENCLAW_NIX_MODE=1`**：`config/nix-mode-write-guard.ts` 对**所有**配置写入无条件 `throw NixModeConfigMutationError`（与文件位置无关），会直接废掉 `doctor --fix`（弹窗自己推荐的 Quick Repair）、插件增删、`openclaw setup`、sticky model 持久化；而 `openclawConfigSync.ts` 正是要运行期写 `openclaw.json`。
- 修法：`openclaw-nix-store-plugin-hardlink.patch` 去掉 `resolveIsNixMode(...) &&` 这道闸，只保留 `isNixStorePluginRoot()` 白名单。安全上站得住——`/nix/store` 只读且只有 root 能建硬链接，该检查要防的「别名 inode」攻击在那儿不可能发生（这本就是上游 Nix 分支写的那段注释的原意，只是被 env 门挡住了）。

两个易混的关卡（报错文案前缀一样，别认错）：`blocked plugin candidate: suspicious ownership (…, uid=…, expected uid=1000 or root)` 是 `discovery.ts` 的**候选筛查**（warning）；`unsafe plugin manifest path` 才是 `manifest-registry`/`discovery` 里 `loadPluginManifest` 的**硬链接拒绝**（error，会触发弹窗）。**在 bwrap 沙箱里复现不了后者**：`/proc/self/uid_map` 为 `1000 0 1`，宿主 uid 不在映射内 → `stat` 显示 65534 → 先撞 ownership 分支；宿主机上 store 文件 uid=1000 才能过筛查、走到硬链接这条。

## `fetchPnpmDeps` 的产物形态

`fetchPnpmDeps` 的 FOD 输出目录里**只有两个条目**：`.fetcher-version`（内容就是版本号）和 `pnpm-store.tar.zst`（整个 pnpm store 的可复现 tarball）。tar 内部是 `./v11/files/<sha512 前两位>/<hash>` 的内容寻址布局；`fetcherVersion = 4` 时 SQLite 的 `v11/index.db` 会被 dump 成 `v11/index.db.sql`（二进制 SQLite 格式不确定，nixpkgs 刻意转成 SQL 文本，再把 `,x'` 换回 `,X'` 以兼容 sqlite 3.53.0 之前的表示）。派生用 `pnpm_12` 时产物**仍是 `v11/`**（不是 `v12/`），所以 nixpkgs fixup 阶段硬编码的 `{v3,v10,v11}` 够用。tar 的可复现参数为 `--sort=name --mtime=@$SOURCE_DATE_EPOCH --owner=0 --group=0 --numeric-owner --pax-option=exthdr.name=%d/PaxHeaders/%f,delete=atime,delete=ctime --zstd`。注意 openclaw 的 lockfile 覆盖全平台（`@anthropic-ai/claude-agent-sdk-*`、`@github/copilot-*`、`@rolldown/binding-*` 等各平台二进制，单个可到 185MB），这个 FOD 下载量极大，首次构建耗时以十分钟计。

## 环境层面的坑（本机踩过，换机器先自查）

- **只读 store 里残留的空 FOD 输出目录会永久堵死该输出路径**：`/nix/store/bg2jq9h4y…-lobsterai-openclaw-runtime-pnpm-deps` 是个 0 字节、`nobody:nogroup` 所有的空目录（外加同名 `.lock`），而 `/nix/store` 对非受信用户是 `Read-only file system`，删不掉。症状很典型：drv 已进入 `building …`，但 `.chroot` 恒为 0 字节、构建器日志一个字节都不出。FOD 的输出路径由 `name + outputHash` 决定，因此**换掉占位哈希（或换 pname）就能换到一条全新且干净的输出路径**——这是绕过，不是修复。
- **`builtins.getFlake (toString <仓库>)` 走 `path:` 语义，会把未跟踪的巨型目录一起拷进 store**：本仓库里 `.tmp-lobsterai` 有 16G，探针表达式里这样引用仓库时 Nix 会尝试拷整棵树并报 `No space left on device`。而 `nix build .#…` 对 git 仓库走 git 语义、只取已跟踪文件（本仓库仅 731 个），又快又不炸。**写探针表达式不要用 `getFlake` 指向仓库，直接 `nix build .#`**；`openclaw-runtime.nix` 这类辅助文件不单独暴露成 flake 属性，要靠构建依赖它的 `lobsterai` 来触发其 FOD。
- **非受信用户（`nix store ping` 报 `Trusted: 0`）改不了 `substituters`**，`--option substituters` 属受限设置会被忽略；若 `~/.cache` 又是只读挂载，`fetcher-cache-v4.sqlite` 写不进去，每次 `nixpkgs#…` 都会去重拉 flake registry——registry 源不可达时这类解析彻底失败，只能靠 `flake.lock` 锁定的 nixpkgs 走 `.#`。同理，`/nix/store/*.lock` 与 store 内残留产物也清不掉。
