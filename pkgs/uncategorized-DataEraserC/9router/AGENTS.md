# 9router 单包经验

- **上游仓库有源码，但本包直接打 npm tarball，不打源码**：`decolua/9router` 是 Next.js 16 应用，`cli/scripts/build-cli.js` 的流程是「`next build --webpack` → 把 `.next/standalone` 拷进 `cli/app/` → 合并完整 server 产物 → 构建 MITM server」，需要 workspace 模式的 tracing root（`NEXT_TRACING_ROOT_MODE=workspace`，`next.config.mjs` 里 `tracingRoot` 取 `..`）、`cli/.build-home` 作 `HOME`、以及完整的 devDependencies（esbuild/nodemon/tailwind/postcss）。npm 发布包（`registry.npmjs.org/9router`）**已经把这一步跑完**，`app/` 下直接是成品 standalone 树（含 `.next-cli-build/`、`node_modules/`、`public/`），因此 `dontNpmBuild = true` 即可，`buildNpmPackage` 只负责装依赖与落盘。
- **tarball 里没有 lockfile，必须自带一份生成的**：`postPatch` 里 `cp ${./package-lock.json} package-lock.json`。生成方式与 nixpkgs 的 `_9router` 一致——**先删 `package.json` 的 `devDependencies` 再 `npm install`**，得到 10 个包、0 个 dev 条目的 lockfile（`esbuild`/`nodemon` 及其全平台 optional 二进制全部消失，npmDeps FOD 从 ~104MB 降到 1.8MB）。`postPatch` 里的 devDeps 剥离与 lockfile **必须成对**：瘦 lockfile（11 条、无 dev）+ 仍带 `devDependencies` 的 `package.json` 会让 `npm ci` 报 `Missing: esbuild@0.25.12 from lock file`（`npm ci` 校验 package.json 里每一项都在 lockfile 中）；反过来带 dev 的 67 条 lockfile + 已剥离 devDeps 的 package.json 能过（npm 只校验前者包含后者），但 27 个 esbuild 条目会白下载。`prefetch-npm-deps` 对瘦 lockfile 算出的哈希与 nixpkgs 同版本 `_9router` 逐字节相同，构建时该 FOD 直接命中 `cache.nixos.org`（1.8 MiB）。
- **`npmFlags = [ "--ignore-scripts" ]` 是必须的**：`cli/package.json` 的 `postinstall`（`hooks/postinstall.js`）会 `npm install` 把 `better-sqlite3`/`sql.js`/`systray2` 下进 `~/.9router/runtime/node_modules`，构建沙箱无网且会写 `$HOME`。运行期 `cli.js` 每次启动都会 `ensureSqliteRuntime`/`ensureTrayRuntime` 重试（失败只打印警告），数据库驱动按 `better-sqlite3 → node:sqlite(≥22.5) → sql.js` 降级，Node 24 下 `node:sqlite` 是内建的第一顺位，因此跳过脚本不影响可用性（实测 `/api/v1/models` 返回 200，日志 `[DB] Driver: node:sqlite`）。另外注意上游在 **Node ≥ 24 时主动跳过 better-sqlite3**（`src/lib/db/driver.js` 的 `tryBetterSqlite` 有 `nodeMajor >= 24 return null`，因其 native addon 在 Node 24 上加载即 SIGSEGV），所以选 `nodejs_24` 反而完全绕开了这个原生依赖。
- **必须删掉 `app/cli/.build-home`**：发布者的打包机上 `HOME` 指向 `cli/.build-home`，该目录被 `.next-cli-build` 的 1105 个 `.nft.json` 追踪文件清单引用，于是 tarball 里带进了构建机的 `~/.9router/db/data.sqlite`（含 `apiKeys`/`usageHistory` 表结构，实测表为空）、`jwt-secret`、`machine-id` 和 `Library/Preferences/nextjs-nodejs/config.json`。这些是构建期状态而非运行期输入（运行期一律走 `DATA_DIR`，默认 `~/.9router`），实测删除后 `/login`、`/dashboard`、`/api/v1/models` 全部正常，故在 `postPatch` 里 `rm -rf` 并在 `postInstall` 断言其不存在。
- **运行期状态全部落在 `DATA_DIR`/`HOME`，不碰 store**：SQLite 库、`jwt-secret`、`runtime/`（CLI 自愈下载的 systray2 等）都写在 `DATA_DIR`（默认 `~/.9router`，可用 `DATA_DIR` 环境变量重定向），实测以只读 store 路径启动后 store 内无任何新增文件。`makeWrapperArgs = [ "--set" "NODE_ENV" "production" ]` 让 Next 走生产分支（`buildNpmPackage` 自动生成的 bin wrapper 会透传该数组）。
- **`sourceProvenance` 取 `binaryBytecode`**：`app/` 下是上游预编译的 Next 构建产物（`.next-cli-build`、静态 chunk、`.nft.json`），不是从本包源码构建出来的；CLI 自身是明文 JS，故不用 `binaryNativeCode`。与 nixpkgs 的 `_9router` 取法一致。
- **验收**：`$out/bin/9router --version` 打印 `0.5.99`（`versionCheckHook` + `doInstallCheck` 已接）；服务侧用 `DATA_DIR=<tmp> $out/bin/9router --no-browser --host 127.0.0.1 --port <p> --skip-update` 起，等 `ss -tlnp` 出现端口后探 `/login`（200）、`/api/v1/models`（200，约 313KB 模型目录）、`/dashboard`（307 重定向到登录）。**不要**只看构建成功——`.nft.json` 里残留的 `cli/.build-home` 路径不影响运行，但缺 `app/node_modules/next` 或 `app/custom-server.js` 会让服务起不来，`postInstall` 已加断言。
- **更新**：`passthru.updateScript = nix-update-script { }`。npm registry 源能被 nix-update 自动识别（`version/npm.py` 只认 `registry.npmjs.org`），实测把 `version` 改回 `0.5.95` 并伪造 src 哈希后跑 `./tools/update-package 9router`，版本与 src 哈希都被正确改回 `0.5.99`；`npmDeps` 哈希由 nix-update 用 FOD 重算。注意 nix-update 用 `json.dumps` 转义属性名，包名以数字开头（`9router`）在 `nix-instantiate -A "grp"."9router"` 与 flake `.#9router` 两种求值下都正常。
