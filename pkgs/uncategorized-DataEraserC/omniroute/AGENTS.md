# omniroute（统一 AI 路由网关，Next.js standalone 部署产物）

- **`doCheck = false` 依据（2026-10-06 实测，v3.8.51 + nodejs_24，全量 `npm test`）**：44830 个用例里 141 个失败，分三类且在 Nix 沙箱（无网络、无宿主程序）下均无法修复：
  1. **网络依赖**：`remote-image-fetch`、`vision-bridge-image-normalize`（真实抓取远端图片并降采样）、`models.dev` 模型目录刷新（`EAI_AGAIN` 后 fail-open 导致断言失败）等；
  2. **宿主外部程序**：`cursor-agent` 可用性探测、Devin CLI spawn（`spawn_failed`）、tailscaled 需要 sudo、Windows certutil 用例；
  3. **宿主工具/环境差异**：`spawnSync git ENOENT`（17 处，changelog-fragment 对账）、`ip ENOENT`（tproxy 路由测试）、端口探测 pid 解析（`ss`/procfs 差异）、并发敏感断言（`usage-history-provider-alias`）。
  上游没有任何离线测试开关（`docs/reference/ENVIRONMENT.md` 无 `OMNIROUTE_TEST_OFFLINE` 之类变量），按仓库规则禁用 checkPhase；同时保留 `doInstallCheck + versionCheckHook`（wrapper `--version` 拦截，见下）。构建期的替代覆盖：`postConfigure` 原生加载 better-sqlite3/wreq-js、上游 prebuild 自带的 `check:native-deps`（33 个 externalised 包解析）、`postBuild` 对 standalone 内 4 个重依赖 `require.resolve`、`installPhase` 路径断言、安装后 versionCheckHook
- **绝不在构建或运行环境设置 `OMNIROUTE_MITM_STUB` / `OMNIROUTE_BETTER_SQLITE3_STUB`**：前者是 Docker 镜像专用补丁（#6344）；后者仅当构建机真的命中 Next build worker 的 native addon teardown SIGABRT（#10060）才可设，一旦设了产物的数据库驱动就是打不开库的 stub（#11343）。本包 webpack 构建未触发该 teardown
- **不要在 `env` 里设 `NODE_OPTIONS`**：`scripts/build/build-next-isolated.mjs` 只在 `NODE_OPTIONS` 不含 `--max-old-space-size` 时才补上游默认 8192（可用 `OMNIROUTE_BUILD_MEMORY_MB` 覆盖）。照抄 Docker 的 `6144` 会挡掉这个默认值，webpack 生产构建在 5877 MB 触顶 `JavaScript heap out of memory` → worker SIGABRT（本包第一次构建的失败根因；Docker 能用 6144 是因为其 node 26 + builder 内存画像不同）
- **`CIRCLE_NODE_TOTAL` 不是死变量**：Next 自己读它决定 page-data worker 数（`workers = N - 1`），保持 `2` 限制并发内存峰值；与 `build-next-isolated` 的 8192 堆上限配合，在 24 GB 内存主机上稳定过构建
- **better-sqlite3 手动 gyp 重建放 `postConfigure`**：与 Dockerfile 同序——`npm ci --ignore-scripts`（`npmRebuildFlags = [ "--ignore-scripts" ]`）后手动执行 hook 注入的 `$npm_config_node_gyp rebuild --nodedir="$npm_config_nodedir"`，随后立即原生加载冒烟；不要让 `npm rebuild` 兜底（Docker 用 `--ignore-scripts` 是刻意的，防 postinstall 网络/平台探测）
- **产物布局**：`.build/next/standalone/.` 整体拷入 `$out/lib/omniroute/`，但 standalone 里只有 `better-sqlite3` 的 partial 同步（assembleStandalone 只拷 `build/`+`prebuilds/`），必须先 `rm -rf` 再拷完整 `node_modules/better-sqlite3`；`migrations/` 与 `dev/run-standalone.mjs` 是 wrapper 启动入口的硬依赖，installPhase 各有断言。wrapper `--chdir` 到该目录并 `--set-default OMNIROUTE_MIGRATIONS_DIR $out/lib/omniroute/migrations`；运行期 `bootstrapEnv` 往用户 XDG 的 `DATA_DIR` 写 `server.env`，绝不能让可写状态落进只读 store
- **wrapper `--version` 拦截的转义**：`--run "if [ \"\$1\" = \"--version\" ]; then exec <node绝对路径> -p \"require('$out/lib/omniroute/package.json').version\"; fi"`——在 `''` Nix 字符串里 `\"`/`\$` 原样传给 bash 的双引号参数，wrapper 行里得到绝对 node 与 store package.json 路径，`env --ignore-environment --chdir=/` 下与 PATH 无关，纯读文件不启动服务（versionCheckHook 唯一的门槛就是输出含版本号）
- **LD_LIBRARY_PATH 双写同一列表**：build `env`（configure 冒烟、`require.resolve`/原生加载可用）+ wrapper `--prefix`（运行期 onnxruntime/keytar/libvips），均为 `lib.makeLibraryPath [ stdenv.cc.cc.lib zlib libsecret ]`；makeWrapper 对同一变量的多个 `--prefix` 会自动去重
- **fixup 的 `noBrokenSymlinks` 会拦下指向构建目录的绝对链接（2026-10-06 实测）**：`npm ci`/assembleStandalone 在 standalone 树里留下一条 `node_modules/global-agent/node_modules/.bin/semver` → `/build/source/...` 的绝对符号链接（上游 `materializeSymlinks` 只处理 Turbopack hashed-module 链接，`.bin` 漏网），fixup 阶段报 `points to /build directory` 构建失败。installPhase 已加通用清理：先把 `-lname '/build/*'` 的链接重定向到 `$out` 内对应路径（不存在则删除），再 `find $out -xtype l -delete` 清掉全部悬空链接（`.bin` 垫片运行期用不到——wrapper 直接调 node）；Nix `''` 字符串里 shell 的 `${var#...}` 要写成 `''${var#...}`，且这段代码要避开 `''` 字面量（字符串终止符）
- **更新**：`passthru.updateScript = nix-update-script { }`；`tag = "v${finalAttrs.version}"` 插值，nix-update 只改 `version` 行即可联动 src；`npmDepsHash` 是顶层属性（`prefetch-npm-deps`，fetcher v1，lockfile 里 10/2820 条无 `resolved` 属 workspace/inBundle 正常）
