# dsh-ego-browser（DSH 浏览器自动化插件）

- **src 用 `fetchFromGitHub` 的 tag（`v0.8.6`），不用 npm tarball**：npm 发布与 GitHub tag 内容一致（`lib/`、`bin/`、`runtime/` 都是预构建入库），但 tag 源码树带 `tests/`，`npm test`（vitest，node 环境，21 个测试文件 / 143 个用例，5 个 e2e 跳过）需要它才能跑
- **上游没有 `package-lock.json`（只有 pnpm-workspace.yaml）**：在包目录提交生成式 lockfile，`postPatch` 里 `cp ${./package-lock.json} package-lock.json` + `chmod u+w`（store 拷入的文件是 444，`npmConfigHook` 的 fixup-lockfile 与 `npm ci` 都要写它）；生成用真实 `npm install --ignore-scripts --no-audit --no-fund`（不能用 `--package-lock-only`，会漏平台 optional 依赖），206 条目
- **不要设 `dontNpmBuild`**：上游有 `scripts.build`（tsdown），`npmBuildHook` 会正常执行；devDeps 全是公开包，构建通过后 `npm pack` 打进 `files` 白名单的 `lib/` 即为重建产物
- **`doCheck = true` + 自定义 `checkPhase` 调 `npm test`**：`buildDshBundle`（`buildNpmPackage` 系）不会把 `scripts.test` 自动接进 checkPhase；vitest 全离线可过（ffmpeg/cast 相关测试用本地 fixture 与 loopback）。Nix 构建里跑通需要两处配套（否则 3 个测试文件解析失败 + 2 个断言失败）：
  - **`preCheck` 把 kernel 的 `@deepseek-ai/*` 范围链进 `node_modules`**：`tests/active-space|env|idle-reaper` 直接 import `../src/index.ts`，它 `import { defineTool } from '@deepseek-ai/dsh-tools'`；该包是 optional peer（registry 只有 0.0.1-rc.1，不满足 `>=0.1.2-rc.1`），只能来自 kernel。`linkKernelNodeModules` 的链接脚本只在 `postInstall`（checkPhase 之后）执行，所以 preCheck 里手工做同样的事（缺则 `ln -s` 到 `${dsh-kernel}/lib/deepseek-harness/node_modules/@deepseek-ai/*`），与运行期链接保持同一来源
  - **`patches = [ ./tests-cross-platform.patch ]` 修两个上游按 Windows 写死的失败断言**：① `selectEncoder` 接受 `platform` 形参但调 `buildCaptureInput` 时没透传，默认落到 `process.platform`（Linux 下走 x11grab/Wayland 分支），导致 win32 场景测试断言 `gfxcapture=hwnd=...` 失败——补一行 `platform,` 透传（生产路径 `platform` 默认就是 `process.platform`，行为不变）；② `profilesFromLocalState` 用 `path.join`（平台原生分隔符），测试却硬编码 `"C:\UD\Default"`——改为 `join("C:\\UD", "Default")`，Windows/Linux 双平台都成立。这两个用例在 Linux 上按原样无法通过，属测试自身问题而非构建环境限制，故打补丁修复而非跳过
- **所有 peer 都是 optional（peerDependenciesMeta 全列）**：`npm install` 不会把 `@deepseek-ai/*` peer 解析进 lockfile；运行时 `@deepseek-ai/schemastery` 由 `linkKernelNodeModules = dshPkgs.dsh.dsh-kernel` 从 kernel 链入（kernel node_modules 自带 3.18.4，`lib/index.js` 唯一的外部 import）
- **`runtimeDeps = [ google-chrome ]`**：插件靠扫 PATH（`google-chrome-stable` / `google-chrome` / `chromium`…）或 `EGO_LINUX_CHROME`、`chromePath` 设置找浏览器；dsh 作为 systemd 服务拉起时 PATH 可能没有用户 profile 目录，把 chrome 钉进 dsh 启动器 PATH（harness `pkgs/dsh/package.nix` 用 `--prefix PATH` 汇总各 bundle 的 `runtimeDeps`）保证 auto-detect 命中；chrome 本来就在本机闭包里，零额外下载
- **`passthru.requiresWeb = true`**：插件带 web 观察窗路由，needsWeb 走 harness 既有机制（同 dsh-chat-import）
- **产物无 `bin/`（package.json 无 `bin` 字段）→ 不设 `meta.mainProgram`**：版本一致性用 `doInstallCheck` + 自定义 `installCheckPhase` 校验装出来的 `package.json` version 等于 `finalAttrs.version`，`postInstall` 再断言 `lib/index.js`、`lib/client.js`、`dsh-plugin.json`、`cordis.patch.yml`、`bin/ego-chrome-wrapper.sh`、`bin/ego-cast-worker.mjs`、`runtime/ego-linux/bin/ego-browser.mjs` 存在（防上游改 files 白名单静默丢文件）
- **兼容性**：manifest 声明 `engines.dsh >=0.1.2-rc.1`、README 实测到 DSH 0.1.5-rc.2，本仓库跟的 DSH 是 0.2.0-rc.2——升级 DSH 后先在会话里跑 `ego_doctor` 确认插件装载正常。另外上游 v0.8.6 忘了同步 bump `dsh-plugin.json` 的 `version`（仍是 0.8.5，package.json 是 0.8.6）——harness 的 bundle 校验不比较两者、装载正常，`dshx list` 显示 0.8.5 属上游问题，不值得为它打补丁
